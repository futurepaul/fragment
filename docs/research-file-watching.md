## File Watching & Incremental Scanning

Research for `fragment sync --watch`: replacing naive N-second polling with an OS-backed watcher plus a resilient incremental scanner. Sources were verified August 2026.

### OS primitives compared

**Linux inotify.** Watches are *per-directory and non-recursive*: to cover a tree you add one mark per directory ([inotify(7)](https://man7.org/linux/man-pages/man7/inotify.7.html)). Each mark consumes a watch descriptor subject to `fs.inotify.max_user_watches` (commonly exhausted; the standard remedy is raising it to 524288 — see the [notify docs](https://docs.rs/notify/latest/notify/) and [webpack troubleshooting](https://webpack.js.org/configuration/watch/#not-enough-watchers)). Events arrive as an *ordered queue* — ordering between directories is guaranteed — but successive identical events may be coalesced, and the queue is finite: on overflow events are dropped and a single `IN_Q_OVERFLOW` (`wd == -1`) is delivered, after which the only correct response is a full rescan ([inotify(7)](https://man7.org/linux/man-pages/man7/inotify.7.html)). Renames produce `IN_MOVED_FROM`/`IN_MOVED_TO` paired by a 32-bit cookie, but pairing is documented as "inherently racy": the pair may be split across reads, interleaved with other events, or missing entirely when a file is moved out of the watched tree (it looks like a plain delete). inotify emits nothing on NFS/network mounts or `/proc`, and no events for `mmap`'d writes. It also cannot tell you *which process* caused an event — relevant for echo suppression later.

**macOS FSEvents.** One stream covers an entire subtree from a single handle — no per-file fd pressure, scales to huge trees ([fswatch docs](https://github.com/emcrisostomo/fswatch)). Events are *coalesced* in time and space and delivered after a configurable latency; historically they identify the *directory* that changed, with file-level detail requiring the `FileEvents` flag (10.7+). A distinctive strength is history: streams can start "since" a persisted event ID (`sinceWhen`/`kFSEventStreamEventIdSinceNow`) and replay changes that occurred while no one was listening — the conceptual ancestor of Watchman's clock. Two caveats: FSEvents' security model means events for files you don't own can be suppressed ([Apple's FileSystemEventSecurity](https://developer.apple.com/library/mac/documentation/Darwin/Conceptual/FSEvents_ProgGuide/FileSystemEventSecurity/FileSystemEventSecurity.html), echoed in [notify's known problems](https://docs.rs/notify/latest/notify/)), and folders can get stuck in a corrupted state that silently stops delivering events ([Livereload's write-up](https://github.com/livereload/livereload-site/blob/master/livereload.com/_articles/troubleshooting/os-x-fsevents-bug-may-prevent-monitoring-of-certain-folders.md), referenced by webpack). **kqueue**, the BSD alternative notify can use (`macos_kqueue`), offers precise vnode events (`NOTE_RENAME`, `NOTE_DELETE`, `NOTE_WRITE`) but needs one open fd per watched object and "scales badly," misbehaving when the fd limit is hit ([fswatch](https://github.com/emcrisostomo/fswatch)).

**Windows ReadDirectoryChangesW.** A single call watches a whole subtree recursively (`bWatchSubtree = TRUE`) with one directory handle ([MSDN](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw)) — the friendliest recursion story. The kernel fills a fixed-size buffer chosen at first call; on overflow the call still returns success but with zero bytes and `ERROR_NOTIFY_ENUM_DIR`, meaning "re-enumerate the tree." Over SMB the buffer is capped at 64 KB (`ERROR_INVALID_PARAMETER` above that), though SMB 3 is otherwise supported. Rename arrives as adjacent `FILE_ACTION_RENAMED_OLD_NAME`/`NEW_NAME` pairs in the buffer. Ordering is reliable within a single returned buffer.

**Semantic summary:** rename is delete+create unless the backend hands you a paired event (cookie on Linux, adjacency on Windows, heuristics on macOS); only Linux guarantees global event ordering; every platform has a defined "I lost events" signal (overflow / `ERROR_NOTIFY_ENUM_DIR`) whose only safe handling is a reconcile scan.

### Classic failure modes

- **Atomic saves.** Most editors write a temp file and rename over the target, so watchers see `delete+create` (or just a rename pair) instead of a modify, and the inode changes under your feet. notify documents that editors vary wildly ([issue #247](https://github.com/notify-rs/notify/issues/247)); webpack's docs tell users to set Vim's [`backupcopy=yes`](https://webpack.js.org/configuration/watch/#vim) and disable WebStorm's "safe write" to avoid it. chokidar's answer is its `atomic` option: if a path reappears within 100 ms of deletion, emit `change` instead of `unlink+add` ([chokidar README](https://github.com/paulmillr/chokidar)).
- **Backup/temp noise**: vim `.swp`, emacs `.#file`/`file~`, Office `~$lock` files generate endless events. Pure filtering problem.
- **Short-lived files**: created-and-deleted between polls are invisible to scanning by definition; watchers see them, but a sync tool should drop candidates that vanish before upload rather than erroring.
- **Event storms**: `git checkout`, `npm install`, build outputs touch thousands of files quickly — the direct trigger of `IN_Q_OVERFLOW` and Windows buffer discards, hence the need for ignore lists (`node_modules`, `.git`, `dist`) and batch-oriented debouncing ([Watchman's inotify tuning notes](https://facebook.github.io/watchman/docs/install#linux-inotify-limits)).
- **Network filesystems**: inotify receives zero remote events ([inotify(7)](https://man7.org/linux/man-pages/man7/inotify.7.html)); notify additionally documents broken WSL→Windows watching ([#254](https://github.com/notify-rs/notify/issues/254)) and Docker-on-M1 failing with OS error 38 ([#423](https://github.com/notify-rs/notify/issues/423)). Polling is the only portable answer there.
- **Cloud-drive placeholders**: OneDrive Files-On-Demand and iCloud dataless files hydrate on access — stat/read itself mutates size and mtime and fires events for content that didn't logically change. Hash-compare before upload prevents spurious syncs; it also protects against loops when another sync tool (including fragment itself) writes into the watched folder.

### Debounce & coalesce strategies

Two families. **Window-aggregation** (webpack's [`aggregateTimeout`](https://webpack.js.org/configuration/watch/#watchoptionsaggregateetimeout), default 20 ms): after the *first* event, wait T for more, then act once on the union — ideal for storms, one rebuild/upload per burst. **Stability detection** (chokidar [`awaitWriteFinish`](https://github.com/paulmillr/chokidar)): hold a specific file's event until its size stops changing for `stabilityThreshold` (default 2000 ms, polled every 100 ms) — directly targets partial-read/torn-upload risk, at the cost of added latency ("Use with caution"). chokidar's `atomic` (100 ms) is effectively per-path debounce against rename-saves.

Per-path debounce keeps one hot file from starving others; global windows collapse bursts into cheap batches. A sync tool wants a hybrid: maintain a pending *set* of paths, extend it on every event, flush when the set has been quiet for T *and* a max-latency cap expires. For markdown vaults, humans tolerate 250–500 ms easily; agent-written files tend to appear atomically (rename) so a modest settle window suffices. Whatever the window, the reader must still defend itself: `stat` → read → `stat` (or hash the bytes actually read) so a file rewritten mid-read is detected rather than uploaded torn.

### Battle-tested implementations

**Facebook Watchman** exists because every consumer was reinventing broken watchers. It is a long-lived daemon that owns the watch state, waits for a newly watched root to *settle*, and errs toward "unsure ⇒ report as changed" ([Watchman overview](https://facebook.github.io/watchman/)). Its key abstraction is the **clock**: instead of wall-clock timestamps ("prone to race conditions"), clients pass back an opaque `c:123:234` id that "ticks as changes are detected rather than as time moves," giving race-free *since-last-query* semantics; named cursors `n:x` persist that per client ([clockspec docs](https://facebook.github.io/watchman/docs/clockspec)). On kernel overflow it "assumes that all the files have been modified and will re-crawl the directory tree" ([install docs](https://facebook.github.io/watchman/docs/install#linux-inotify-limits)); it drains events on a dedicated thread, refuses to follow symlinks, and warns of "very poor results" on distributed filesystems. Case sensitivity bites it on mixed fleets (case-insensitive macOS vs case-sensitive Linux volumes), which is why it tracks per-root case sensitivity explicitly. Lesson for fragment: adopt the *abstractions* (change-ticking cursor, overflow ⇒ recrawl, settle-on-start), not the daemon — a CLI shouldn't require users to run a service.

**Rust `notify` (v6→v7→v8)** is the ecosystem default. `recommended_watcher()` selects per platform: inotify on Linux, FSEvents on macOS by default (`macos_kqueue` opt-in), ReadDirectoryChangesW on Windows, `PollWatcher` elsewhere. Its ["Known Problems"](https://docs.rs/notify/latest/notify/) section is required reading: network filesystems may emit nothing; macOS suppresses unowned-file events; editor behavior varies; deleting a watched folder's parent loses the event ([#403](https://github.com/notify-rs/notify/issues/403)); very large watch sets may drop events ([#412](https://github.com/notify-rs/notify/issues/412)); `PollWatcher` with `compare_contents` is the escape hatch for pseudo-filesystems and permission-poor setups. **[notify-debouncer-full](https://docs.rs/notify-debouncer-full/latest/notify_debouncer_full/)** layers on the fixes everyone ends up writing: stitches `Rename{From,To}` into one event (even retroactively re-pointing earlier buffered events), merges duplicate creates/modifies, emits one Remove for a deleted directory, and — via the `file-id` crate's device+inode/file-index `FileIdMap` — survives atomic saves that swap inodes. **[fswatch](https://github.com/emcrisostomo/fswatch)** confirms the per-backend ranking independently (FSEvents "no known limitations"; inotify's laundry list; kqueue's fd exhaustion; poll ≈ linear cost). **chokidar**'s hard-won knobs — `useFsEvents` default on macOS, `usePolling` as the documented fix for network/WSL/Docker where "it is typically necessary…to successfully watch files over a network", `EMFILE`/`ENOSPC` triage — map almost one-to-one onto the fallback policy below ([README](https://github.com/paulmillr/chokidar)).

### Incremental scan hygiene (even with a good watcher)

Every mature tool keeps a **cheap stat scan** alongside the watcher, because events are hints, not truth. `mtime + size` is the classic short-circuit: O(n) syscalls, no reads — but mtime has coarse granularity on some filesystems, is preserved by `cp -p`/git operations, and cloud clients churn metadata, so **periodic full-hash verification** remains the reconciliation step of last resort (this is exactly Watchman's overflow posture, generalized). **TOCTOU** between noticing and reading is unavoidable; the defense is verify-after-read (stat/hash the bytes you got) so stored state always describes content you actually observed. **Crash safety**: persist scanner state by write-temp → fsync → rename-in-same-dir, versioned, treating corrupt state as "resync from scratch." **Restart cost**: if state records `path → {hash, size, mtime, file-id}`, a restart needs only one stat-only sweep diffing against state — hashing only genuinely changed files — rather than a full recrawl. **Root moved/renamed**: capture `(st_dev, st_ino)` of the root at startup and re-check it periodically; if the path now resolves elsewhere, stop and ask rather than syncing a stranger's folder (inotify only tells you `IN_MOVE_SELF`; the parent-watch trick of [notify #403](https://github.com/notify-rs/notify/issues/403) helps). **Symlink loops**: recurse without following links (`walkdir` default, and Watchman's stated policy) and carry a visited `(dev, ino)` set as a belt-and-braces guard.

### What "reliable enough" means for agent-driven workflows

Human editing implies bursts of a few files with well-behaved saves. Agent-driven workflows are harsher: many files may appear at once, writers range from atomic-rename generators to streaming appenders (logs), and files can disappear between detection and read. The bar therefore shifts from *"never miss an event"* (no backend promises that — overflow is a designed-in possibility on every OS) to ***"the local view converges on true vault state"***: events provide fast convergence; scheduled reconciliation guarantees eventual correctness; every individual upload is defensive (skip vanished files quietly, retry locked ones, hash-verify content, make uploads idempotent via content hashes so replayed events are no-ops).

**Recommendation for fragment**

1. **Crates**: `notify = "8"` via `recommended_watcher()`; `notify-debouncer-full = "0.7"` with its default `FileIdMap` (gets rename stitching + atomic-save inode tracking for free); `walkdir = "2"` (no symlink following) for scans. No new heavy dependencies; no Watchman daemon requirement.
2. **Topology**: one recursive watcher rooted at the vault root — notify expands this to per-directory inotify marks internally, while FSEvents/ReadDirectoryChangesW get recursion natively. Apply ignore rules at the event layer before debounce: `.git/`, `.obsidian/`, `.trash/`, `node_modules/`, `*.swp`, `*~`, `.#*`, `~$*`, fragment's own state file.
3. **Pipeline**: raw events → debouncer timeout **300 ms** (`--debounce-ms`, clamp 50–5000) → merged into a persistent pending-set keyed by canonical path → flusher uploads in batches. Upload gate per file: `stat` → read → re-`stat`/hash-check; `ENOENT` skips, mid-read mutation retries.
4. **Fallback cadence**: if the native watcher errors at startup (ENOSPC, network mount, M1-Docker) or dies later, log a warning, fall back to `PollWatcher` at **5 s** (`--poll-interval`), and keep the stat-sweep reconciler regardless. Detection heuristic for network mounts: compare `st_dev` of the vault root against local-device expectations at startup and prefer polling when ambiguous.
5. **Reconciliation**: stat-only sweep of the tree every **60 s** (`--rescan-secs`) diffing mtime+size against state; lazy full-hash audit (e.g. hourly or `fragment verify`). Any watcher error event triggers an immediate out-of-band sweep — the Watchman recrawl rule.
6. **Persistence** (so restarts never recrawl hashes): `<vault>/.fragment/state.json` (or SQLite if metadata grows) holding `{schema_version, root_dev, root_ino, files: {path → {hash, size, mtime_ns}}}`. Written atomically (temp + fsync + rename) after each successful batch, throttled to ≥1/s. Startup: validate schema + root identity → one stat-only diff sweep → sync only deltas. Missing/corrupt/mismatched root ⇒ clean full initial sync. This is fragment's equivalent of Watchman's clock: a durable "changes I've already seen" cursor that survives restarts.
7. **Config surface** (Finite CLI conventions): `--watch-backend {auto,native,poll}`, `--debounce-ms`, `--poll-interval`, `--rescan-secs`, `--json` status output including current backend, pending-set depth, and last-rescan timestamp, so hosted-agent skills can report watcher health without hidden knowledge.
